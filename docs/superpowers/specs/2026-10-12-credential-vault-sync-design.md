## 1. Goal and what the user decided

Goal: full **bidirectional exchange of password, passkey and TOTP** between WSurf and Apple Passwords, using only the system's native, user-confirmed credential exchange, with every WSurf-side change recoverable.

Decided by the user (not re-litigated here):

1. Bidirectional native exchange of password, passkey, TOTP. The Apple-side limits in §13.1 are **accepted** (importer decides skip/add/replace; no receipt per item; WSurf cannot see or undo Apple's side).
2. **Several vaults per profile**, which may share an unlock passkey or use different ones. At creation the user chooses only *New passkey* or *Use existing WSurf passkey*.
3. **History (revisions) and a linked Trash are mandatory and automatic for every vault.** No option, setting, flag or code path turns them off. Nothing is auto-emptied. Only explicit purge and profile erase remove recovery data, and purge removes it from the **current store only**: `Credentials.vault.pre-v2`, Time Machine and any other copy outside the store are untouched and are never deleted automatically (§11.4).
4. Trash delete/undelete is a **MOVE**: one authoritative credential with its complete history; no secret-bearing duplicate left in Trash.
5. Passkeys are retain-all: re-registration appends.
6. Manual editor: URL fields accept Enter/Shift-Enter and typed comma/space as separators in both website fields; TOTP is entered as a raw key or `otpauth://` only (no QR). The editor cannot create a passkey. (The editor itself is another worker's scope; §12 only fixes its contract with this design.)
7. The goal is implementation + PR + Pro build + Air deploy. **This written spec was approved by the user on 2026-10-12, together with the PR→`main` and G6 deploy path** (design approval only: runtime gates remain unverified; no tag/publish/release authorization).

Not allowed: CSV as sync, QR, Apple autofill as a transport, background/automatic sync, retention off, any move of a credential between two independent active vaults, any claim that WSurf "synced". (The only MOVE is an active vault ↔ **its own linked Trash**.)

Non-goals of this build: moving a credential between independent active vaults; cross-vault merge; deleting a vault (only profile erase deletes vaults); per-item skip of unsupported exchange data (today's fail-closed stays); SQLCipher or any new dependency; a Keychain item, entitlement, App Group or Secure Enclave key for this feature (§6.6); in-app quarantine, reset, "acknowledge missing" or high-water-mark features (not requested; §6.4, §6.7).

Risks found in source that the design **must** close (each has an acceptance item in §16):

- **R1 same-ID passkey overwrite.** `replace(.passkey, .passkey)` copies the incoming passkey (key material included) over the target keeping the local id (`XA:317-324`), and conflicts are matched only by `rpID` + `credentialID` equality; key bytes and `userHandle` are never compared (`XC:559-571`). A passkey with the same `rpID`+`credentialID` but a different key would overwrite a private key on one click. §13.3 removes passkey replace and makes that case a non-overridable hard conflict at both the review (`K` `choose`) and the codec (`XA` `validatedDecisions`).
- **R2 frozen inherited dates on export.** Export writes `created: metadata.created, lastModified: metadata.lastModified` from the stored exchange blob (`XE:86-89`), so an edited item re-exports with its stale Apple dates. §12.2 fixes it.
- **R3 token fate.** `receive` drops a second token while one is pending/claimed/staged (`K:190-198`; the caller gets `false` and shows nothing, `WSurf/App/BrowserApplication.swift:195-197`). `claimImport` marks the token consumed *at claim* (`K:209-216`): a later cancel, lock, epoch change or stale preview ends the transfer and the token cannot be reused. The user must be told, truthfully, that the transfer was discarded and must be started again from Passwords (§13.5).
- **R4 profile by window.** The import is bound to the profile of the settings page the user reviews from (`WSurf/App/BrowserApplication.swift:188-205`, `K:209-216`), not to a profile named by the transfer. §13.5 requires profile and vault to be shown in the preview and bound to it.
- **R5 draft secrets.** `CredentialDraft` carries passkeys and TOTP it does not expose (`private(set) totp/passkeys`, `S:89-119`). Save must not drop or rewrite them, and an unchanged save must be a **no-op** (§11.1), or every edit would manufacture a revision.
- **R6 ids are not identity.** Exchange ids/metadata come from the exporter; nothing proves stability or authenticity (§13.3).
- **R7 extension is static.** The credential-exchange extension has no data channel to the app and receives no vault data; nothing in this design may rely on it.

## 3. Architecture in one page (DESIGN)

- One **credential store** per profile: a dedicated, hard-fail GRDB SQLite file `Credentials.store` (never `AppDatabase`, never in-memory fallback), holding the registry of vaults, per-vault sealed records, sealed heads and sealed journals.
- A **vault** has role `active` or `trash`; every active vault owns exactly one trash vault (created in the same transaction). Each vault has a distinct random 32-byte DEK. Trash DEK is wrapped under its source's DEK.
- **Discovery** (what vaults exist, before unlock) is **provisional** until an unlock authenticates it. Authentication is a **registry** row (canonical catalog of every vault row digest) MAC'd with a random **registry key** that is sealed inside every active vault's head under that vault's DEK and never derives or opens any DEK. Plain anchors only detect initialization/missing store: the store file, a stub in the legacy path, and a storeID witness in the profile's `UserDefaults` (§6).
- **Integrity** per vault: sealed head, live-row digests and an append-only sealed hash-chained journal of history rows, all verified in full, streamed with bounded memory, inside one database snapshot **before any access is granted** at every unlock (§7).
- **Access**: per-vault manager, lease, epoch and grant (§9). One assertion opens only the vault(s) chosen in that prompt.
- **Exchange**: reviewed import into one explicit destination vault; handoff export from one explicit source vault; no deletion propagation; no clocks (§13).

## 4. Vault model, keys, grants

4.1 **Vault** = `{vaultID, profileID, role, ordinal, createdAt}` in the registry, plus sealed `{name}` in its head. Names may identify the user, so they are **never** stored in plaintext: a locked vault is labelled by creation ordinal ("Vault 1", "Vault 2") and shows its real name after unlock. (Safe default; no product question.)

4.2 **DEK per vault**, random, regardless of unlock credential. "Same key" in the user's words = same passkey wrapping several DEKs; "different keys" = a different passkey. Same code; only the supplied `VaultUnlockProof` differs. HKDF binds profileID+vaultID (`C:433-438`) so one PRF output yields different wrapping keys per vault. State in the creation UI that sharing a passkey means one authenticator compromise exposes all vaults sharing it (a choice, not isolation).

4.3 **Creation choices.** *New passkey*: today's registration flow (fresh userID + prfInput). *Use existing WSurf passkey*: an **assertion** (no registration) over a `(credentialID, prfInput)` pair read from a wrapper's plaintext metadata of a vault of this profile, whose PRF output is the creation proof. Offerable passkeys = those already enrolled in some vault of this profile (safe default). No silent enrollment. **UNVERIFIED (gate G1):** that a bare assertion on an existing credential yields a PRF output sufficient for `create`. Source shows `create` accepts any valid proof (`V:40-60`) but nobody has run it natively. If it fails the UI states that this passkey cannot be reused for a new vault; there is **no fallback** (no silent new passkey, no unwrapped vault, no copy of an existing wrapper).

4.3a **Acceptance of *Use existing WSurf passkey*.** The error path above (a distinct message, no fallback) is required for platforms or credentials that cannot supply a proof, but it is **not** acceptance of the feature. The feature is accepted only when a known-valid PRF credential enrolled in an existing vault is natively reused to create a new vault that then unlocks with that passkey alone (gate G1). If the platform cannot do it, that is reported **blocked**, never as a pass and never as a reduced scope.

4.4 **Trash DEK hierarchy.** `DEK_trash` is random; stored as `keyWrap` = AES-GCM(DEK_trash) under `DEK_source`, AAD binds profile, source vault, trash vault, link nonce. Opening the source yields the trash: no second prompt per delete/undelete. Consequences, shown in UI/spec text: the trash has no independent unlock and follows its source's enrollments; removing a credential from the source (`removeUnlock`) stops it opening both; this is **not** cryptographic revocation (a held DEK, cached grant, or older file/`.pre-v2` backup still decrypts what it decrypted).

4.5 **Grants.** An assertion proves a credential; the grant it yields applies only to the vault(s) the user is opening in that prompt. The PRF output is used to unwrap and is not retained. A shared passkey never opens another vault silently; "unlock all vaults sharing this passkey" is a separate explicit action (not built unless later requested).

4.6 Purge / Empty Trash need **fresh native authorization**: a new assertion with a credential enrolled in the *source* vault, not the cached lease.

## 5. Store layout (DESIGN, exact)

Directory = `profile.supportDirectory` (`WSurf/Profiles/Profile.swift:48-56`). Files:

| File | Content | Authenticated? |
|---|---|---|
| `Credentials.store` (+ `-wal`, `-shm`) | GRDB database, `secure_delete=ON`, `foreign_keys=ON`, `journal_mode=WAL`, `synchronous=FULL` | by sealed contents + registry MAC (§6.5, §7) |
| `Credentials.vault` | after migration: **stub** (below); before: legacy v1 envelope | stub: not authenticated; a guard, not evidence |
| `Credentials.vault.pre-v2` | byte copy of the v1 file made before migration; never auto-deleted, rewritten or renamed | n/a |
| `Credentials.store.migrating` | **pending store**: built by migration (§10) or first-vault bootstrap (§8) before cutover; renamed to `Credentials.store` only after cutover | n/a |
| `Credentials.lock` | empty file; `flock` target, held per operation only (§15) | n/a |
| `Credentials.vault.swap` | the prepared stub before cutover; after the cutover swap, the displaced original v1 file until it is checked (§10 step 8) | n/a |
| `Credentials.vault.cutover-v1[-UUID]` | a v1 file displaced at cutover that was **newer than the migrated copy** (§10 step 8): integrity evidence, never deleted, renamed, merged or cleared by WSurf | v1 envelope, encrypted under its own wrappers |
| `Credentials.scratch/` | ephemeral directory (`0700`, files `0600`) for verification ledgers; emptied at open and after every use (§7) | n/a |

**Stub** (`Credentials.vault` after migration) = binary plist `{format: 2, profileID, storeID}`; no secrets. Old builds read it via `decodeEnvelope`, `validateEnvelope` requires `format == 1` (`C:285`) → `corruptVault`; Settings then reports it and never offers Create (`S:399-412`; `V:45`). That is the **old-reader fence**. Rule: the global `format` constant is **not** bumped; wrapper AAD keeps the frozen label/format `1` (introduce `wrapperFormat = 1` for wrapper AAD, `C:440-448`), so carried-over wrappers stay byte-identical and valid. The new store defines its own schema constants. If the stub is absent an old build offers Create and may write a v1 file: that is why a missing stub is never a normal writable state (§6.3 row 7, §6.8).

Tables (all text ids are canonical UUID strings; blobs are AES-GCM combined `nonce‖ciphertext‖tag`; **no stored digest or chain column is trusted**: every digest and chain value is recomputed from the stored sealed bytes):

```
store_meta(id INTEGER PRIMARY KEY CHECK(id=1), schema INTEGER, storeID TEXT, profileID TEXT)
vault(vaultID TEXT PRIMARY KEY, role TEXT CHECK(role IN('active','trash')), ordinal INTEGER,
      createdAt REAL, wrappers BLOB,        -- active: the existing wrapper list, byte-identical; trash: NULL
      keyWrap BLOB)                         -- trash: DEK_trash under DEK_source; active: NULL
head(vaultID TEXT PRIMARY KEY REFERENCES vault, revision INTEGER, sealed BLOB)
record(vaultID TEXT, recordID TEXT, kind TEXT, ownerID TEXT, subject TEXT, version INTEGER, sealed BLOB,
       PRIMARY KEY(vaultID, recordID))
journal(vaultID TEXT, seq INTEGER, sealed BLOB, PRIMARY KEY(vaultID, seq))
registry(id INTEGER PRIMARY KEY CHECK(id=1), revision INTEGER, catalog BLOB, mac BLOB)
```

- `kind` ∈ `account` (live, active vault), `revision`, `trashEntry`, `tombstone`. `ownerID` = owning account id. `subject` ∈ `account | password | totp | passkey | metadata`: which credential or part the row belongs to (TOTP has no id field today, `A:178-195`; none is invented; a passkey is identified inside the sealed body by its existing `id`).
- Plaintext columns (`vaultID`, `recordID`, `kind`, `ownerID`, `subject`, `version`, sizes, counts, `role`, `ordinal`, `createdAt`) are visible to a disk reader but carry no name, URL, username or secret. This is an **engineering choice, not a user-approved disclosure**; vault names are sealed in the head (§4.1).
- Each row's AEAD AAD = `"WSurf credential store" ‖ schema ‖ storeID ‖ profileID ‖ vaultID ‖ recordID ‖ kind ‖ ownerID ‖ subject ‖ version`. It binds the **row's own version**, not the head revision, so a commit does not re-seal history; a plaintext column that disagrees with its AAD fails at decrypt.
- `head.revision` plaintext equals the revision inside the sealed head; CAS happens on the plaintext inside the same SQL transaction, then the sealed value must agree on open.
- Hot path: unlock verification (§6.8, §7) runs once per grant; afterwards `snapshot()` reads only `kind='account'` rows of the active vault and checks each against the head's `liveCatalog` digest (O(live) hashing). Revisions/Trash are read by indexed query and decrypted one page at a time; autofill and WebAuthn never touch history rows.
- **Limits (exact, chosen here):**
  - Live data per active vault: **unchanged from today**: ≤ `CredentialVaultLimits.accounts` = 1,000 accounts, total live plaintext ≤ `CredentialVaultLimits.payloadBytes` = 4,000,000 B, existing per-field caps (`A:44-47,78,149,187`), ≤ 32 wrappers (`C:8-14`). A migrated vault therefore always fits.
  - Every history row (`revision`, `trashEntry`, `tombstone`) plaintext ≤ **8,000,000 B** (a conservative cap). By construction a row holds at most one account's data (≤ 4,000,000 B, as the live cap guarantees), plus provenance and envelope fields ≤ 4,096 B, plus (single-credential entries only) a display label ≤ 512 B; so the cap is never reached by valid data and no valid live account can become undeletable. A whole-account `trashEntry` holds the account snapshot **once**; its Trash label is derived from that snapshot while listing (entries are decrypted one at a time), never stored as a second copy. A metadata revision holds the typed metadata projection only (§11.1), never password, TOTP, passkey or basic-auth values. AES-GCM adds 28 B per sealed row.
  - History: **no logical limit** on row count, total bytes or per-transaction bytes/rows; bounded only by disk. Nothing is dropped or truncated to fit.
  - A journal row holds ≤ 1,000 ops; a transaction appends as many journal rows as needed.
  - ≤ 16 active vaults per profile (each with its linked trash) (engineering choice; bounds the registry).
  - Import: the existing exchange budget (`XC:136-143`) is unchanged and bounds an import transaction.
  - A write that exceeds a *live* limit is refused whole with a distinct error naming the limit. Deleting at the live cap always works (delete moves to Trash, which has no logical cap), so there is no cap deadlock; purge never adds live data.
  - Disk-full / SQLite error: the transaction rolls back; the **logical committed values** (heads, rows, registry as seen through the API) are unchanged. Physical WAL/page contents may change and are not claimed identical.
- **Schema constants (final; nothing here is left to the plan):** store `schema = 2`; `wrapperFormat = 1` (frozen wrapper AAD); a row's `version` starts at 1 and increases by 1 per rewrite of that row; row AAD label `"WSurf credential store"`; registry label `"WSurf registry v1"`; every AAD/MAC field is written in the typed encoding of the next bullet (variable-length fields, i.e. text and byte strings, carry a UInt32 big-endian length prefix; UUIDs, integers, enum tags and the other fixed-width fields are written at their fixed width with no extra wrapper), so concatenation is unambiguous; the registry MAC message is `text(registryLabel)` followed by `bytes(catalog)`; SQLite `busy_timeout` 5000 ms, then a `storeBusy` error with nothing written; history lists are read in pages of 50 rows; the "Verifying" state (§7) is shown when verification exceeds 250 ms; vault `name` ≤ 64 characters; ≤ 16 active vaults; ≤ 1000 ops per journal row; ≤ 32 wrappers per vault.
- **Byte encoding (fixed; changing any of it requires a new `schema`).** Integers are UInt64 big-endian (8 bytes) unless a width is stated; lengths and counts are UInt32 big-endian; UUIDs are 16 raw bytes in AAD/MAC/digest inputs (the SQL columns hold the canonical lower-case string); text is UTF-8 with a UInt32 length prefix and no normalization; byte strings have a UInt32 length prefix; booleans 1 byte (0/1); optionals a 1-byte tag (0 absent, 1 present) then the value; dates the IEEE-754 Float64 bit pattern as UInt64; arrays a UInt32 count then elements in the stated order, sets sorted by the 16-byte id ascending. Enum tags (UInt8): role `active`=1 `trash`=2; kind `account`=1 `revision`=2 `trashEntry`=3 `tombstone`=4; subject `account`=1 `password`=2 `totp`=3 `passkey`=4 `metadata`=5; journal op `add`=1 `remove`=2; direction `in`=1 `out`=2; scope `account`=1 `credential`=2. Every AAD, MAC input, sealed head, journal row, registry catalog and the §12.3 content-hash input is the fields listed in this spec, in the listed order, in this encoding. Row bodies (`account`, `revision`, `trashEntry`, `tombstone`) carry the existing account Codable encoding of the v1 payload; they are not re-canonicalized, because every digest in this design is over **stored sealed bytes**, never over re-encoded plaintext. This section fixes bytes, not any user interface.

## 6. Discovery, authentication, tamper and disappearance (engineering design for contract gates §9.1–9.2; unproven until the §16 tests and native gates pass)

### 6.1 Three separate secrets/anchors; what each can and cannot do

| Item | Scope | Can it open a DEK? |
|---|---|---|
| **Unlock grant** | one vault: the user's passkey PRF output unwraps that vault's wrapper → its DEK (§4.5, §9) | that vault only |
| **Registry key RK** | 32 random bytes generated once at first store creation; sealed inside **every active vault's head** under that vault's own DEK; used **only** as the HMAC-SHA256 key of the registry row (§6.5) | **never**: it is not an input to any KDF, wraps nothing, derives nothing |
| **A3 witness** | non-cryptographic marker: `{storeID}` | no |

A holder of any one active vault's DEK can read RK and could therefore forge the registry; that holder already reads that vault. Stated, not hidden (§6.7). Unlock-grant scope is never widened by RK: unlocking vault A yields RK but opens no other vault's DEK, head or rows.

### 6.2 The three anchors (exact)

| Anchor | Where | Content | Role |
|---|---|---|---|
| **A1 store** | `Credentials.store`: `store_meta`, `vault`, `registry` rows | `storeID`, vault set, MAC'd catalog | the data and the authenticated registry |
| **A2 stub** | `Credentials.vault` | `{format:2, profileID, storeID}` | old-reader fence; cross-check of `storeID` |
| **A3 witness** | `UserDefaults` of the profile (`ProfileSettingsStore.defaults(for:)`, key `io.wsagency.wsurf.credentialVault.storeID`), outside `supportDirectory` | `storeID` string | **initialization / missing-store witness only**: "a store has existed for this profile" |

A3 is non-cryptographic; it detects accidental loss and replacement, not an adversary. It may be **absent**; only an **absent** A3 is ever set (after an authenticated unlock, §6.8 step 7). A **present** A3 whose `storeID` differs from the store or stub is **never repaired, overwritten or ignored**: it fails closed (§6.3 rows 5 and 8) with no grant. It is written only with a `storeID` obtained from an authenticated source (creating process, migration, or a verified unlock) and cleared only by profile erase (`ProfileSettingsStore.forget`). It never records revisions, vault lists or acknowledgements.

### 6.3 State machine at open, before any unlock (reads never write)

Inputs: A2 ∈ {v1 envelope, stub, absent, unreadable}, A1 ∈ {present, absent, unreadable} (present = file opens as SQLite with `store_meta`), A3 ∈ {absent, present}. "agree" = every present `storeID` (stub, `store_meta`, A3) and `profileID` equal. Everything before an unlock is **provisional**: lists show ordinals and "not yet verified". **Presence rules (Director clarification, 2026-10-12):** A3 is **present** when its `UserDefaults` object exists, whatever its type or content; an object that is not a parsable `storeID` string is present and can never agree, so it is never "absent" (it never permits first run, row 7/4's absent branch, or `setWitnessIfAbsent`). A1 and A2 are **absent** only when the file verifiably does not exist; any existing file whose open, read, header, decode or `store_meta` read fails is **unreadable** (rows 11/12). Failing to enumerate the directory (permissions, not a directory) proves neither absence nor "no leftovers": it fails closed (`unreadableStore`) before the table, never `firstRun`/resume; only a directory that verifiably does not exist reads as empty.

### 6.4 Fail closed: exact behaviour, no concealing recovery

A fail-closed state shows its cause in plain words and lists the **absolute paths** of every file involved (`Credentials.store`, `-wal`, `-shm`, `Credentials.vault`, `Credentials.store.migrating`, and `Credentials.vault.pre-v2` **if it exists**, named as "a copy of the vault from before migration, which does not contain later changes"). The only action is **Retry** (re-evaluate). WSurf never moves, deletes, resets or overwrites anything to get out of a fail-closed state, never clears A3, stub or any integrity evidence to proceed, never offers Create, and never guesses which file is right. Recovery is the user restoring files from a backup outside WSurf; profile erase (the existing path) is the only thing that clears A3. No quarantine, reset, "start over" or "acknowledge missing" action exists in this build.

The listed paths also include `Credentials.vault.swap` and every `Credentials.vault.cutover-v1*` when present, the latter named "a v1 vault file that was replaced during migration and is newer than the migrated copy".

### 6.5 Registry: authenticated catalog of the whole store

`registry.catalog` = canonical encoding (fixed field order, sorted by `vaultID`) of `{schema, storeID, profileID, registryRevision, vaults:[{vaultID, role, ordinal, createdAt, wrappersDigest, keyWrapDigest, headRevision, headDigest}]}` where each digest is SHA-256 of the **stored** bytes (`vault.wrappers`, `vault.keyWrap`, `head.sealed`; absent = 32 zero bytes). `registry.mac` = HMAC-SHA256(RK, `"WSurf registry v1"` ‖ catalog).

- **Every** transaction that changes any head, wrapper list, key wrap or the vault set rewrites the registry row in the same transaction (revision+1, new MAC). A single-vault write recomputes only that vault's entry (and its linked trash's), copying the others from the registry it verified. Under `BEGIN IMMEDIATE` the writer re-reads the current registry, verifies the MAC with RK, and verifies that its own vault's entry still equals what its session read (else `staleRevision`); another vault's concurrent commit therefore never invalidates it.
- The registry commits: complete vault ids and roles, wrapper/keyWrap/head digests and head revisions. A removed, added, swapped, re-wrapped or rolled-back vault row, head or wrapper list fails the catalog comparison in §6.8.
- No vault's DEK is needed to *check* the registry (only RK, obtained by unlocking any one active vault) and no other vault is decrypted by checking it.

### 6.6 Explicit non-assumptions

No new Keychain item, entitlement, access group, App Group, Secure Enclave key or system service is introduced, and none is needed: RK lives inside vault heads. The existing `keychain-access-groups` entitlement is for unrelated autofill vaults and is not relied on. If the user later approves a Keychain/OS witness it can replace A3 without changing the file format.

### 6.7 Bounded limits (stated, not solved)

1. **Total anchor loss** (A1, A2 and A3 all gone) reads as a first run. Absolute deletion cannot be detected without an independent durable witness; A3 is the only witness and is deliberately outside the support directory and non-cryptographic.
2. **A holder of any one DEK** can read RK and re-MAC a forged registry (they already read that vault); a same-user writer of both directory and preferences defeats A3. The registry resists anyone without a DEK.
3. **Whole valid snapshot rollback**: restoring an older, internally consistent store (registry, heads, rows, wrappers all from one earlier moment, including a subset byte-identical to an earlier consistent state) passes every check and loses later changes without warning. No high-water mark or acknowledgement is added; this is a known limit.
4. The pre-unlock vault list is unauthenticated (provisional).

### 6.8 Unlock verification order: nothing is granted before step 8

0. **Lock first, before any snapshot.** Choose the operation lock (§15) from the provisional §6.3 state: EXCLUSIVE when the stub is absent (row 7), SHARED otherwise. Acquire it **before** opening any read transaction, re-read A2/A1/A3 under it (if that shows the other mode is needed: release, reacquire, restart; never upgrade in place), and hold it until step 8 has published.

Then, for the vault the user selected, inside **one read transaction** (a single coherent SQLite snapshot):

1. Anchors (§6.3) must be non-fail-closed.
2. Unwrap the selected active vault's DEK from `vault.wrappers` with the PRF output; open its head (the head AAD binds the wrapper digest, so wrappers are authenticated); take RK and `storeID`/`profileID`; both must match the store.
3. Verify the registry MAC with RK; verify `registryRevision` consistency; compare the **whole catalog** to the actual `vault` and `head` rows: same set of vault ids and roles, same digests and head revisions. Only stored metadata and sealed bytes are **hashed** for this comparison; no other vault is decrypted or modified. Any difference ⇒ **store-level fail closed** (§6.4); no vault of this profile is granted. Missing rows name the vault by ordinal.
4. Verify the selected vault's linked trash: row present, `keyWrap` opens under the DEK, link nonce equals on both heads.
5. Run §7 verification for the vault and for its trash. Failure ⇒ that vault is `integrityFailure`: no grant (not even read-only), no writes; other vaults are unaffected because the catalog still verifies.
6. If the stub is absent (row 7), with the EXCLUSIVE lock already held since step 0: re-check that no v1 file exists (else row 3 fail closed) and create the stub with an atomic create-if-absent (`renamex_np(..., RENAME_EXCL)` from a temp file written with `F_FULLFSYNC`, then `fsync` of the directory; contents derive from the authenticated `storeID`/`profileID`), so an old build's v1 file can never be overwritten by it.
7. If A3 is **absent**, set it to `storeID`. A present A3 that differs never reaches this step (§6.3 rows 5, 8).
8. Publish the grant (`VaultAccess`) to the manager **while still holding the lock**, carrying the verified head and registry revisions; if the manager's access epoch or generation changed during verification the result is discarded (no stale publish). Then release the lock. Every later commit CASes against those revisions.

### 6.9 What each disappearance does (every combination reduces to the §6.3 table + §6.8)

| Gone | Result |
|---|---|

## 7. Per-vault integrity: head, live rows, journal (DESIGN, exact)

**Sealed head** (under the vault's DEK; AAD = schema, storeID, profileID, vaultID, `head.revision`, wrappers digest, keyWrap digest):

```
{ storeID, profileID, vaultID, role, revision, name,
  registryKey,                                 // active vaults only; trash heads never hold it
  link{peerVaultID, nonce},
  liveCatalog:[{recordID, version, digest}],   // active vault: every live account, ≤ 1000; digest = SHA-256 of stored sealed row bytes
  journalSeq, chainTip,                        // last journal seq and chain value
  historyCounts{revision, trashEntry, tombstone} }
```

**PLANNING CLARIFICATION: password-save policy storage (added 2026-10-12 during implementation-plan review after the original approval; ACCEPTED by the user on 2026-10-12 by the instruction to proceed with the plan that carries it, see §18).** The v1 payload persists `blockedPasswordOrigins` (`CredentialVaultCrypto.swift`: at most 4,096 canonical origins, counted inside the 4,000,000 B live budget) and §11.1 requires it to be preserved, but the head above has no field for it. This adds **no new capability and changes no user data**; it names where existing data lives. The sealed head of an **active** vault gains one field after `registryKey`: `blockedOrigins: [text]` (trash heads carry an empty array).

- *Bytes:* array = UInt32 count, then each origin as text (§5 encoding), sorted ascending by UTF-8 bytes, no duplicates. V1 fails (`integrityFailure`) for a head whose array is unsorted, duplicated, over 4,096, or holds a string that is not a canonical origin (`CredentialAccount.origin(for:)` round trip, as v1 validation requires today).
- *Authentication:* the field is inside the sealed head, so it is under the head's AEAD (AAD per above) and covered by the registry's `headDigest`; replacing or editing it is detected like any other head change.
- *Update:* a policy change is a head-only transaction (CAS `head.revision`, revision+1, registry entry updated). It writes no live row, revision, journal row or history row. This replaces, for this one case, the §11.1 wording that a blocked-origin change rewrites the live row. A policy update equal to the stored set is a true no-op (nothing written).
- *Account commits and wrapper changes* copy the head's set unchanged.
- *Migration (§10 step 4)* copies the v1 payload's set verbatim into the first active head; nothing else is added or dropped.
- *Snapshot* returns the head's set as `blockedPasswordOrigins`.
- *Limits:* unchanged: count ≤ 4,096, each entry a canonical origin, and origin bytes plus live account bytes ≤ `CredentialVaultLimits.payloadBytes`, validated by the existing payload validation.

**Journal row** (sealed under the vault's DEK, AAD `schema ‖ storeID ‖ vaultID ‖ seq`). Plaintext = `{seq, prevChain, transfer?, ops}`; `transfer = {transferID, direction, scope, ownerID, subject?, liveRecordID, liveVersion, entryRecordID}`; `ops:[{op, recordID, kind, ownerID, subject, version, rowDigest}]`, ≤ 1000 ops per row; `rowDigest` = SHA-256 of the history row's stored sealed bytes (for `remove`, of the row removed). A commit that adds or removes any **history** row (`revision`, `trashEntry`, `tombstone`) appends journal rows; live-only edits and `lastSignedAt` commits do not. **Every MOVE appends a journal row with the same `transfer` header to each side's journal even when it moves zero history rows**: a delete of an account with no history still writes a `transfer` row (empty moved set, one `trashEntry` add) on the Trash side and an `out` row on the source side. `liveRecordID`/`liveVersion` name the live account row removed (delete) or added/changed (undelete) on the active side; `entryRecordID` is the `trashEntry` row. A moved history row keeps its `recordID`, `kind`, `ownerID`, `subject` and **origin `version`** (the version in its AAD is the origin version, never renumbered) when re-sealed under the other vault's DEK; its ciphertext and therefore `rowDigest` legitimately change (different vault in the AAD, new nonce), so a MOVE comparison never uses digests across vaults. Chain: `chain_0` = 32 zero bytes; `chain_n = SHA-256(chain_{n-1} ‖ SHA-256(sealed_n))`, **recomputed from the stored sealed bytes** at verification; the head holds `(journalSeq, chainTip)`.

**Verification (runs in full at every unlock for the vault and its linked trash, in one read snapshot, before any grant, §6.8 step 5; streamed, memory O(one row + SQLite page cache))**

- **V1 head**: opens; AAD fields, `storeID`, `profileID`, `vaultID`, `role` match the rows; plaintext revision equals the sealed revision; link nonce matches the peer head.
- **V2 live rows**: for each `liveCatalog` entry the row exists, the SHA-256 recomputed from its **stored sealed bytes** equals `digest`, version and AAD fields (`kind`, `ownerID`, `subject`) verify by decrypting; the number of `kind='account'` rows equals the catalog length (no extra rows).
- **V3 journal chain**: rows `seq = 1…journalSeq` exist, contiguous, no extras; each decrypts with its own `seq` and `prevChain` equal to the running chain; the final recomputed chain equals `chainTip`.
- **V4 history ledger**: apply every journal op, in order, to the ledger table `expected(recordID PRIMARY KEY, kind, ownerID, subject, version, rowDigest, seen)` in the verification scratch database (below). An `add` of an existing id, a `remove` of an absent id or a `remove` whose fields differ from the stored expectation fails. Then stream every stored history row of the vault: recompute SHA-256 of the **actual stored sealed bytes**, require `kind`, `ownerID`, `subject`, `version` and `rowDigest` to equal the ledger entry, decrypt once (discarding the plaintext) to verify the tag and AAD, mark `seen`. Finally `seen` count = ledger count = `historyCounts` for each kind, and no ledger entry is unseen. Deleted, substituted, replayed, foreign or extra history rows fail.
- **V5 transfer pairs** (historical, never against current catalogs): group the journal rows of the verified pair (source and its linked trash) by `transfer.transferID` into scratch tables `transfers(transferID, side, direction, scope, ownerID, subject, liveRecordID, liveVersion, entryRecordID)` and `transferRows(transferID, side, recordID, kind, ownerID, subject, version)`. Each `transferID` has exactly one `out` group on one side and one `in` group on the other (a delete: `out` on the source, `in` on Trash; an undelete the reverse); `scope`, `ownerID`, `subject`, `liveRecordID`, `liveVersion` and `entryRecordID` are identical; the moved history rows removed on the `out` side equal, as a set of `(recordID, kind, ownerID, subject, version)`, those added on the `in` side excluding the `trashEntry` row (added on the Trash side by a delete, removed there by an undelete). The key never includes `rowDigest`. An account with zero history verifies: both journals still hold the `transfer` row with an empty moved set. **V2 verifies the current rows and catalogs; V5 verifies only the paired historical headers and their moved row sets.** A historical transfer header never asserts, on its own, that its account is absent from or present in the **current** live or Trash catalog, because later transfers change that: a delete → undelete → delete sequence (and any longer alternation) must verify, each transfer checked only against its own pair. Any mismatch within a pair fails.

**Verification scratch (replaces any SQLite `TEMP` use).** Ledger tables live in a scratch SQLite file `Credentials.scratch/<random UUID>.db` inside the profile's support directory, `ATTACH`ed to the verification connection; never in `TEMP`, never in the OS temporary directory, and `temp_store`/`temp_store_directory` are never changed (they are process-global). Directory `0700`, file `0600`, `journal_mode=OFF`, `synchronous=OFF`. Contents are limited to opaque ids, small integers (`version`, `direction`, `side`), the `kind`/`subject` enum values and 32-byte SHA-256 digests of **ciphertext already stored in the store**; never plaintext, names, URLs, usernames, decrypted values or ciphertext bytes. The file is unlinked on success, on error and on cancel (`defer`); every leftover in the directory is removed at the next store open and at profile erase. It holds no integrity evidence, so removing it does not conflict with §6.4. If an unlink fails, verification still completes and a non-fatal warning shows the path. The ids and digests it holds are the same class of plaintext as the §5 columns (an engineering choice, not a user-approved disclosure).

Failure of any V-check ⇒ `integrityFailure` for that vault and its trash: **no new write may ever promise complete history**, so no grant is issued, not even read-only. There is no cache and no "live continues" mode: verification runs at every unlock; cost is O(history bytes), streamed, cancellable (cancel ⇒ no grant, scratch removed), with a "Verifying" state in the UI. Cost is never a reason to skip a check; the measured cost on the Air target is reported by gate G4 as an observation, not as a condition for weakening the design.

No Merkle tree, accumulator or new primitive: SHA-256 and AES-GCM and HMAC-SHA256 only. Additive/XOR set hashes are not used (forgeable at scale); a chain plus an exact ledger is boring and exact.

**Atomic commit.** One SQLite transaction per logical operation, `BEGIN IMMEDIATE`: CAS `head.revision` (and registry per §6.5), write changed rows, append journal rows, write new head(s), rewrite the registry row. A MOVE (delete/undelete) writes both vaults' rows, journals and heads in the same transaction, in a single process holding the source DEK and the derived trash DEK, **streaming** one history row at a time (decrypt, re-seal, write). Any error (disk full, SQLite, cancellation) rolls back the whole transaction; nothing is truncated or partially moved. A write that cannot also store its recovery rows is refused whole (I3).

## 8. Creating a vault: registry update needs ONE authorized vault, not all

The registry MAC needs RK, which any unlocked active vault holds. A vault creation therefore needs **exactly one** existing vault authorized in this session (or none, for the very first vault), and decrypts **no other** vault:

1. **First vault of a profile** (state row 10), under the EXCLUSIVE lock: generate RK; proof from a *New passkey* registration (§4.3). Build the pending store `Credentials.store.migrating` (vault, linked trash, heads, empty journals, registry); commit, `wal_checkpoint(TRUNCATE)`, close every connection, require no `-wal`/`-shm`, `F_FULLFSYNC`, `fsync` the directory; reopen and run §6.8 steps 2–5, close again with the same sidecar and fsync checks; write the prepared stub to `Credentials.vault.swap` (`F_FULLFSYNC`); create `Credentials.vault` with the atomic create-if-absent `renamex_np(..., RENAME_EXCL)` (fails if any v1 file appeared: nothing is overwritten and the §6.3 state applies) and `fsync` the directory; rename the pending store to `Credentials.store`, `fsync`; set A3. A crash before the stub exists leaves only the pending store and/or `.swap`: §6.3 row 10 then fails closed with their paths and Create is never offered; WSurf never discards them. A crash after the stub exists is row 6 (resume at the next unlock). No partially initialized artifact ever enables Create.
2. **Further vault, *Use existing WSurf passkey***: the user picks a passkey enrolled in some vault S of this profile (safe default: only those); the **same assertion** unwraps S's DEK and authenticates S by running §6.8 **steps 1–7 only** (S's DEK, RK and the registry are verified under the same operation lock; **step 8 is never run**), and supplies the proof that wraps the new DEK. This is internal verification, not a grant: no `VaultAccess` is ever published to S's manager, so there is no publish-then-revoke window. S's DEK, RK and the assertion output are dropped when creation ends; creating a vault never publishes or extends a lease for S, so S does not become available to autofill, WebAuthn or export as a side effect. The native prompt names S ("Unlock Vault N to authorize creating a new vault; it will not stay open"). If the user wants S open they unlock it separately (full §6.8). If S has not passed §6.8 steps 1–7 the creation does not proceed.
3. **Further vault, *New passkey***: requires a vault that is **already unlocked in this session** (the UI first asks the user to unlock one); creation never proceeds without an authorized vault, and the user is never required to unlock every vault. (Engineering default, no product question.)
4. Build: `vaultID`, `trashVaultID`, random `DEK`, `DEK_trash`, link nonce; wrappers for the proof exactly as `create` does today (`V:40-60`); the new active head seals RK (same RK), name, link, empty catalog; the trash head and `keyWrap`; empty journals.
5. One transaction (§6.5): re-read and verify the registry with RK, check its revision, insert both vault rows, both heads and the registry row with the two new entries (`ordinal = max+1`, ≤ 16 active), revision+1, new MAC. Other vaults' rows, heads and wrappers are **not decrypted, re-sealed or modified**; the already MAC-verified registry supplies their catalog entries, and their stored bytes are only hashed by the §6.8 unlock comparison.
6. The profile **default vault** pointer is a plaintext non-secret preference (`io.wsagency.wsurf.credentialVault.defaultVault`, vault id); it may name a locked vault (§14). A3 is unchanged (same `storeID`).

If the existing-passkey assertion cannot yield a usable proof (gate G1) the UI says so; there is no fallback (§4.3).

- **Per-vault manager** (`CredentialManager`, per `(profileID, vaultID)`), each with its own 300 s lease, epoch, lock sources (sleep, screen lock, termination, timeout, profile switch: `M:10-12,154-169`) and `commit` check `authorizedEpoch == access.epoch` (`M:376-380`). A per-profile `CredentialStore` object owns the GRDB queue and the §6 state; `forProfile(profile)` is replaced by `forVault(profile, vaultID)` at the four consumer sites. Trash views and operations use the **source** vault's manager; there is no separate trash lease.
- `retire(profileID:)` (profile erase, `M:126`, `WSurf/Profiles/Profile.swift:107`) drains all vault managers, closes the store, then the existing directory removal runs. Profile erase remains the only erase path; it destroys all vaults, trash, tombstones, A3 (`ProfileSettingsStore.forget`) and states that irreversibly (counts shown when readable, "may contain recoverable items" when locked). Original profile cannot be erased (`WSurf/Profiles/Profile.swift:102`).
- `addUnlock` / `removeUnlock` keep today's authorization separation (`M:350-362`; `V:146-210`) but become a store transaction on `vault.wrappers` + re-sealed head (the head AAD carries the new wrappers digest; `revision` advances) + the registry row (§6.5). They never touch `record`/`journal`. `removeUnlock` does **not** rotate the DEK (stated plainly as today); it must invalidate cached grants/leases for the removed credential in the same step; the confirmation text says older copies (Time Machine, `.pre-v2`, the removed credential still holding a DEK) may still decrypt. Restore/undelete APIs cannot reach wrappers (not in their signatures). Each unlock performs §6.8 before `beginAccess` publishes the lease.

## 10. Migration of vault #1 (DESIGN)

Trigger: the user's **first successful unlock of the legacy vault** in a build with this feature (the DEK is needed to seal rows and wrap `DEK_trash`). Open and status checks never write. Before it starts the confirmation says: quit every other WSurf build, including older ones, that uses this profile. That precondition only reduces overlap; it is **not** what guarantees nothing is lost: the atomic swap (step 7) and the displaced-bytes check (step 8) are.

The whole migration runs under the EXCLUSIVE operation lock (§15), from step 1 to step 10. If it cannot be taken within 5 s the migration aborts with "another WSurf process is using this profile's credentials; quit it and retry", nothing written.

1. Re-read the anchors under the lock: must be §6.3 row 1 (legacy) with no `Credentials.vault.cutover-v1*`. Read the v1 file bytes **B0** once; decrypt with the user's unlock proof from B0 itself, so the DEK and accounts correspond to B0.
2. **Backup**: `Credentials.vault.pre-v2`. Absent ⇒ write a temp file, `F_FULLFSYNC`, rename, `fsync` the directory. Present ⇒ it must be **byte-identical to B0** and is reused untouched; any difference ⇒ abort with nothing changed and the path shown. It is never overwritten, deleted or renamed by WSurf, and an identical leftover from an earlier crashed attempt never blocks a retry.
3. A leftover `Credentials.store.migrating` (and its `-wal`/`-shm`) is removed **only now**, because step 1 verified v1 as authoritative and step 2 verified the backup equals B0; before that it is never discarded. A leftover `Credentials.vault.swap` that decodes as a **stub** is removed too (derived data); one that decodes as a v1 envelope is displaced evidence (§6.3 row 6 state, step 8), never removed here.
4. Build `Credentials.store.migrating` with a fresh `storeID`: the vault row (same `vaultID`, same `profileID`, wrappers **byte-identical**), one `account` row per account with the **exact** decoded `CredentialAccount` (same account ids, passkey ids/`credentialID`s, `exchangeAccountID/ItemID`, metadata, dates; new date fields nil), the head with a freshly generated RK, a freshly created linked trash vault (`DEK_trash` wrapped under the existing DEK; **no** extra prompt, no new passkey), empty journals, the registry row. Invent no ids; reconstruct no history (none exists). Commit; `PRAGMA wal_checkpoint(TRUNCATE)`; close every connection; require no non-empty `-wal`; `F_FULLFSYNC` the database file; `fsync` the directory.
5. Verify: reopen the closed file, run §6.8 steps 2–5 with the held DEK, decrypt every row, compare the canonical account list with B0's payload, compare the wrapper bytes with B0's. Then **close every connection again, confirm no `-wal`/`-shm` remains (else `wal_checkpoint(TRUNCATE)` and close again; if they still exist, abort with v1 authoritative), `F_FULLFSYNC` the file, `fsync` the directory**: no open SQLite handle exists on the pending file when it is later renamed.
6. Write the stub (from the authenticated `storeID`/`profileID`) to `Credentials.vault.swap`, `F_FULLFSYNC`, `fsync` the directory.
7. **Commit point**: `renamex_np(Credentials.vault.swap, Credentials.vault, RENAME_SWAP)` atomically exchanges the two files; `fsync` the directory. If the volume does not support `RENAME_SWAP` (`ENOTSUP`/`EINVAL`) the migration aborts with nothing changed; there is no fallback to a non-atomic replacement.
8. **Displaced-bytes check**: `Credentials.vault.swap` now holds whatever v1 file was at the legacy path at the instant of the swap. Compare its bytes with B0. **Equal** ⇒ it is a byte copy of `.pre-v2`: unlink it, `fsync`. **Different** ⇒ an old build wrote after B0 was read: **no grant**; rename it to `Credentials.vault.cutover-v1` (`-<UUID>` suffix if that name exists; never overwritten), `fsync`, and **fail closed** (§6.3 row 13). The stub, the pending store and that newer v1 file are all preserved; no automatic rollback, no merge, no discard; the paths are shown. The newer v1 stays encrypted under its own wrappers; reconciling it is the user's job outside WSurf.
9. Rename `Credentials.store.migrating` → `Credentials.store`, `fsync` the directory.
10. Set A3; open the store; the first normal unlock continues from §6.8 (which re-verifies under the lock).

**Exact failure states.** Steps 1–6 fail or crash: v1 is untouched and authoritative (the backup is a byte copy; a leftover `.migrating` waits for step 3 of the next attempt). Crash inside step 7: the swap is atomic, so either the old state or (stub at `Credentials.vault`, displaced v1 at `.swap`). Crash after 7 (before 8, or between 8 and 9): stub + `.swap` (if not yet unlinked) + `.migrating` = §6.3 row 6: the **next unlock** takes the EXCLUSIVE lock, performs step 8 first (a displaced file different from `.pre-v2` ⇒ `cutover-v1` and fail closed), then verifies `.migrating` (§6.8 steps 2–5) and only then performs 9–10; if that verification fails nothing is renamed or discarded and the state fails closed with the paths and the `.pre-v2` path shown. Crash between 9 and 10: store + stub, A3 absent: row 4. An old build that writes **after step 8**: its atomic file replace overwrites the stub with a v1 file; once `Credentials.store` exists that is row 3 (fail closed, both preserved); before step 9 completes it reads as row 1 again (legacy), and a later migration starts over from that newer v1 (the old pending store is derived from B0 and is replaced under step 3). An old build write overlapping the swap lands either in the displaced file (caught by step 8) or on the stub (row 3 / row 1 as above). In every ordering the old writer's data survives as a file or as the authoritative v1; the only residual is that the user may have to reconcile two files by hand, stated here.

Downgrade consequence, stated: after migration old builds show a corruption-style error and cannot open the vault; changes made after migration are not in `.pre-v2`; `.pre-v2` is stale, still holds the pre-migration payload under the old wrappers (so anything later purged from the store remains decryptable from it by whoever can unlock those wrappers), is **not** covered by purge, is never auto-deleted by WSurf (the user may delete it outside WSurf), and its path is shown wherever purge or a fail-closed state is explained. Wrapper trap resolved by §5 (frozen wrapper AAD, no global format bump).

## 11. Revisions, Trash, MOVE, purge

### 11.1 What creates a revision (semantic diff inside the store commit, so every writer is covered)

A revision is an **earlier value being superseded or removed**, stored in the active vault with `ownerID` = account id:

| Kind | Revision when | Never |
|---|---|---|
| password | password, username or `basicAuthenticationMetadata` **replaced** (the old value becomes a revision) | identical re-save; **removal** (see below) |
| TOTP | secret/algorithm/period/digits/issuer/userName **replaced** (old value becomes a revision) | code display/ticks/copies (not persisted); **removal** (see below) |
| account metadata | `displayName`, `origins`, `loginURLs`, user-meaningful `exchangeMetadata` fields change; the **typed projection** `{displayName, origins, loginURLs, exchange}` is stored (never password, TOTP, passkey or basic-auth values) | `created`/`lastModified` in `exchangeMetadata` changing alone; id refresh |
| passkey | **removal** (→ Trash) | `lastSignedAt`, `exchangeFIDO2Metadata` refresh, **add** (nothing superseded: no fabricated old version) |
| never | `lastSignedAt`, `remoteLastObservedAt`, `lastImportedAt`, `lastExportHandoffAt`, `migratedAt`, inherited Apple dates, `blockedPasswordOrigins`, wrappers | |

**Removal of a single credential by any path** (explicit delete, a draft that clears the password or TOTP, an import/replace that removes one) is the §11.2 single-credential MOVE: the removed value **and every earlier revision of that same `ownerID`+`subject`** go to Trash in one transaction and **no revision row for that credential remains in the active vault**; a removal never creates an active-vault revision that duplicates a secret already in Trash.

**Metadata revisions and the exchange blob.** `exchangeMetadata` is written only by the exchange codec from the typed `ExchangeMetadata` struct (`XC:124-,276-286`: accountName, email, fullName, collections, subtitle, created, lastModified, favorite, tags), which has no password, TOTP or key field. A metadata revision stores that blob **re-encoded from the decoded struct** (unknown keys are not carried); a blob that does not decode as that struct is never copied into history and the commit that would supersede it is refused with a named error. The opaque `exchangeAccountID`/`exchangeItemID` are non-secret and travel in the projection. A removed password or TOTP value therefore exists only in its own `password`/`totp` revision rows (which move to Trash and are purged with the entry), never in a metadata revision (acceptance item 17).

**Persistence classes (this replaces "semantic equality ⇒ write nothing").**
- A **true no-op** is a commit whose **complete persisted payload** (every field of every account, including `lastSignedAt`, `remoteLastObservedAt`, `lastImportedAt`, `lastExportHandoffAt`, `migratedAt`, exchange and passkey metadata, `blockedPasswordOrigins`) equals the stored payload. It writes nothing: no row, no head bump, no registry change. An editor save with an unchanged draft yields an identical payload and is a true no-op; the draft preserves unexposed secrets/passkeys untouched (R5).
- A commit whose semantic content (§12.3 hash) is unchanged but whose persisted payload differs (passkey `lastSignedAt`, an import observation, an export-handoff stamp, an exchange-metadata refresh, a blocked-origin change) **is persisted**: the live row is rewritten, the head revision advances and the registry updates. It writes **no revision, no journal row and no history row, and it does not set the account's content `modifiedAt`**.
- Row plaintext and provenance (`recordedAt` WSurf clock, `cause` explicit or nil=unknown, never defaulted) are immutable.

### 11.2 Delete = MOVE active → its own linked Trash (one transaction, §7)

Two granularities, both streamed and atomic:

- **Whole account**: the live account row and **every revision row owned by that account** (all `subject`s: password, totp, metadata) move to the trash vault: one `trashEntry{scope: account, ownerID, accountSnapshot}` (the snapshot is stored once; the listing label is derived from it) plus the revision rows (same `recordID`s and origin `version`s, re-sealed under `DEK_trash`; identical plaintext and provenance, with the `transfer` journal rows of §7 on both sides).
- **Single credential** (password, one passkey, or TOTP): the account stays live **with its siblings and its metadata revisions untouched**; only that credential's value goes into `trashEntry{scope: credential(kind[, passkeyID]), ownerID, label}`, and only revision rows with that `ownerID` **and** that `subject` (password or totp; passkeys have no revisions) move with it. `label` = the owner's display name and first origin, each ≤ 256 B, display-only text copied because the owner may later change or be deleted; no sibling credential value is copied. An account left with nothing valid (`A:43`) takes the whole-account path.

Trash is never an autofill/WebAuthn/import/export source by type; its vault is never listed as selectable. Disk, SQLite or limit failure ⇒ the delete is refused whole and the account stays; there is no logical size limit that can block a delete (§5).

### 11.3 Undelete = MOVE Trash → its source vault, collisions BLOCK

Checks first, all blocking, never overwriting; the rules differ by scope and are exact. **Whole-account entry:** live `recordID` (account id) already present; any live `exchangeAccountID`/`exchangeItemID` equal to the entry's; any live origin+username overlap; any live passkey with the same `rpID`+`credentialID`. **Single-credential entry:** the owner account must exist live (else blocked: "the account this belongs to is not in the vault"); the checks **exclude the owner account itself** for `recordID`, exchange ids and origin+username (the owner is the intended target, so its existence never blocks); instead they are slot-specific: a password or TOTP entry is blocked when the owner's password/TOTP slot is already occupied (even by a different value); a passkey entry is blocked when **any** live passkey in the vault (owner included) has the same `rpID`+`credentialID`; and any **other** live account carrying an exchange item id equal to the entry's, or an overlapping origin+username with the restored credential, blocks. Blocked ⇒ a preview names the clash and **nothing is written**. There is **no alternative restore action** (no "restore as new", "restore into Y" or "replace Y"): the user resolves the clash by editing or deleting the conflicting live item (itself recoverable) and retrying. A passkey that collides on `rpID`+`credentialID` with a different key or `userHandle` is the §13.3 hard conflict. On success the credential and its **complete** revision history move back in one transaction (with the `transfer` journal rows of §7 on both sides) and the `trashEntry` and its history rows are removed from Trash; only non-secret journal rows (transfer header, ids, direction) remain. Exactly one secret-bearing copy exists. Copy: "Restore saved copy in WSurf", never "reactivate".

### 11.3a Restoring an earlier revision (distinct operation; not undelete)

In an account's Earlier versions the user may restore a **password, TOTP or metadata revision**. A preview shows the resulting account and names the secrets that will be superseded; the apply is an ordinary semantic commit (§11.1): the current value becomes a **new revision**, the chosen revision is left unchanged (immutable, not moved, not deleted), nothing is placed in Trash and no Trash entry is required. It is blocked when the result would be invalid (e.g. duplicate or invalid origins). Passkeys have no revisions; a removed passkey is only recoverable by undelete.

### 11.4 Purge, Empty Trash, tombstones

Explicit only; fresh native authorization (§4.6); no timer, age, count or capacity trigger. The **confirmation** lists items/counts and states: *"This removes the selected items and their history from WSurf. Encrypted remnants and backups may remain: older database pages, Time Machine or other backups and, if this vault was migrated, the backup file `Credentials.vault.pre-v2` (path shown), which still contains the vault as it was before migration. WSurf never deletes those copies."* Purge is a **logical row purge, not secure erasure**: it deletes the selected entries and their revision rows and replaces them by an encrypted `tombstone` row (entry id, accountID, kind, non-secret external ids incl. exchange ids and passkey `credentialID`, dates, purge event; **no** password, TOTP seed or key material), journaled as `remove`/`add`. Its guarantee is exactly: after the purge commits, no **currently reachable** record of that vault or its Trash (live row, revision/history row, Trash entry, tombstone, journal row) yields the secret when decrypted and enumerated. Old ciphertext may remain in SQLite freelist pages, the WAL or filesystem/SSD remnants and in backups, and the DEK is not rotated, so a holder of the DEK and such a remnant could still decrypt it; WSurf does not claim otherwise. **Logical capacity never blocks purge**: it is not limited by the live account/byte caps, the record-admission limits or the active-vault count (it admits no live data and a tombstone is bounded by one non-secret row, ≤ 4,000,000 B by the §5 row cap and in practice a few hundred bytes). Physical exhaustion of the filesystem is different: a full disk can make the transaction fail; the failure is atomic and honest (nothing changes logically, the message says the disk is full and what to free), and no other deletion is attempted to make room. Purge is a store transaction that never goes through the ordinary commit and never touches wrappers. `secure_delete=ON` and a WAL checkpoint/truncate after a purge are best-effort hygiene only, with no guarantee for freed pages, WAL, filesystem or SSD remnants.

## 12. Dates, metadata, editor contract

12.1 `createdAt` on an account is set **only** when WSurf itself creates it (known creation). Migrated and imported accounts keep it nil (unknown stays unknown; an imported Apple `created` stays in inherited metadata and is never shown as WSurf's content date). A semantic edit sets `modifiedAt`; it never fabricates `createdAt`. `migratedAt` is a separate event. Per-credential local events: `lastImportedAt` (an applied import), `lastExportHandoffAt`, `remoteLastObservedAt`; none of them means "synced". All new fields are optional Codable so v1 payloads decode.

12.2 **Export dates (fixes R2).** Export an item's `lastModified` = account `modifiedAt` when WSurf changed it; inherited Apple dates only while the content hash equals the bound observed base; otherwise nil. Never `Date()`; never inherited dates on edited content; `timestamp` stays exporter-level (`XE:86-89`). No date resolves any conflict, no "newer wins", no future-date clamp, the wall clock is untrusted; any displayed date says whether it is Apple-reported or a WSurf event.

12.3 **Content hash** (for base/no-op/comparison): SHA-256 over a canonical encoding of the semantic content of one credential, **excluding** every timestamp, `lastSignedAt`, signature counters and exchange dates.

12.4 **Manual editor contract** (the editor is another workstream's code; this is the behaviour this design relies on). Fields exist today: `websites` (one HTTPS address per line → `loginURLs` + `origins`) and `extraOrigins` (→ `origins` only); no "primary" attribute, ordering flag or new storage is introduced; origin and passkey `rpID` are different namespaces and one is never derived from the other (`S:104-106,189-212`, `WSurf/Settings/Pages/CredentialSettings.swift:507-510`, `A:62-71,83-114`).
- Typed comma or Space, **both** website fields: only on the key-input path, unmodified, no marked text, no selection, caret at the end of the line, and the current line trims to a **valid** address for that field ⇒ the delimiter becomes `"\n"` and the line shows as a link. Otherwise the character is inserted literally (a second delimiter on the new empty line or after an invalid line stays literal; there is no "repeat collapses" rule).
- Enter, Shift-Enter, Option-Enter and keypad Enter insert a plain `"\n"` (never U+2028) and never Save; IME marked text goes to the IME untouched.
- Paste, drop, dictation, text replacement, autocorrect and IME commit insert verbatim: no splitting, no conversion, no normalization. Nothing is normalized while typing; existing save-time sanitization (`parseSites`/`validate`) is unchanged.
- Tab/Shift-Tab move focus; Esc is not intercepted; links are editable text: clicking a link places the caret and **never navigates, opens a URL, opens a browser tab or invokes any link action**.
- TOTP is entered as a raw key or `otpauth://` text only (no QR); the field is a `SecureField` and the secret is afterwards shown only as a code (`CredentialSettings.swift:572`). The editor cannot create a passkey; passkey editing is deletion-only.
- Editing name or websites yields no semantic change, no revision and no event/date change for any secret the user did not change: `draft.account()` currently reassigns `password/passkeys/totp` even when untouched (`S:155-187`), so the comparison against the draft's base is field by field (§11.1). A stale draft (`draft.revision` changed before Save) is refused with a message that says to reload; the draft stays open.
- UNVERIFIED native behaviours: Return bypassing the sheet's default Save, real typed comma/Space reaching `keyDown` across layouts and not for paste/IME, link styling and click interception, undo after attributes are re-applied, Shift-Enter yielding `"\n"`, VoiceOver. They are native acceptance items, not claims.

## 13. Exchange (Apple ↔ WSurf)

### 13.1 Accepted Apple-side limits (user decision)
Native, user-confirmed, both directions. The Apple importer decides skip/add/replace; no per-item receipt; WSurf cannot see, guarantee or undo Apple-side trash/history; WSurf's restore only restores its own saved copy. Copy never says "synced", "Apple accepted" or "updated in Passwords".

### 13.2 Two things, never conflated
(a) **Accepted remote observation / bound base**: set only by an item that actually arrived through a user-applied import (or an explicit user pairing of a local record with that item): content hash, `remoteLastObservedAt`, pairing of remote item to local credential. (b) **Export-candidate snapshot**: `lastExportHandoffAt` + content hash of what WSurf handed to the system. (b) never advances (a), never marks anything "unchanged", and cannot classify any remote outcome. A later import may be compared with (b) as information only.

### 13.3 Identity and conflicts (fixes R1, R6)
- Exchange ids are a **hint, not authority**. An id match counts only together with a bound local record and a previously explicitly accepted pairing. An id match without one, or matching several local records, ⇒ `ambiguous`, explicit user review. A bound pairing whose incoming **content differs** is never "identity ambiguous": it is the ordinary `remote-changed` / `both-changed` classification below (a legitimately changed remote secret stays a reviewable change). The only hard, non-overridable identity conflict is the passkey cryptographic fixed identity of the next bullet; an exchange-id/content disagreement is never one.
- Never auto-match by site+username (multi-account sites exist). A user may explicitly target an account (`.add(targetAccountID)` / `.replace(target)`).
- No clock decides anything.
- **Passkeys.** Identity is the **normalized cryptographic identity**: decode the incoming key with `P` `importPKCS8` and re-encode with `exportPKCS8` (what import already does, `XC:357-366`), compare the resulting public key; raw DER byte inequality for the same key is **not** a conflict. For the same `rpID` (case-folded) + `credentialID`: same public key **and** same `userHandle` = `unchanged` (differences in `userName`, `userDisplayName`, FIDO2 metadata or dates are ignored, local metadata stays, nothing is written); a **different public key OR a different `userHandle` = non-overridable hard conflict**: shown, that passkey is not imported, no replace, no "import anyway", no default button, no destructive-confirmation path, the local one stays and the user can only leave it out. A different `credentialID` = append as a distinct passkey (retain-all). There is **no passkey `replace` operation**: the `(.passkey,.passkey)` branch (`XA:317-324`), the `.replace` choice for passkeys in `K` `choose` and the replace validation in `XA` `validatedDecisions` are deleted. Import hard-codes `backupEligible=true`, `backupState=false`, `algorithm=-7` (`XC:358-371`) and non-ES256 keys are rejected (`A:134`); re-export advertises exactly those stored values. Passkey editing is deletion-only: no key/ID/handle editing UI.
- Classification against the **destination vault only**: `new`; `unchanged` (hash equals bound base and local equals it); `remote-changed`/`local-changed`/`both-changed` only with a bound observed base (three-way on content hash); `no-common-base` (two-way review); `previouslyRemoved`; `ambiguous`. "Absent from this transfer" is "not observed", never removal, age or divergence.
- Decisions per credential default **keep**: `keep`, `add as separate`, `replace` (password/TOTP only). `both-changed`/`no-common-base` never auto-resolve. `replace` writes the superseded value as a revision in the same transaction and the preview names every secret that will be superseded (extends `removesStoredPasswordOnReplace` to TOTP).
- `previouslyRemoved`: incoming non-secret identifiers match an `inTrash` entry or a tombstone of the destination vault (or an accepted prior pairing). Content similarity to live Trash entries is a **hint** only; purged items are matched by identifiers, never by secrets. Default skip with {restore via restore preview, import anyway as new, skip}. Best-effort, and the UI says so; changed ids re-import as new. **No silent re-import from Trash.**
- Unsupported or malformed records keep today's **whole-payload fail-closed** (any bad record rejects the whole import: `K:244`, `XC:251-253,313`, a 26.4 item with extensions on an older OS rejects the file). The message states that nothing was imported and shows the record position without content. No skip-malformed mode, no queue, no automatic retry.
- TOTP: identical seed and parameters = `unchanged`; different seed, or same seed with different digits/period/algorithm/issuer, = conflict reviewed without revealing the secret (`XC:552` only treats "both have a seed" as a conflict today). Login rules: a username-only record counts as a login (`XC:589-591`); an incoming username-only item never removes or hides a stored password, and a default merge that would throw `invalidData` (`XA:284`) is shown as a conflict, not silently dropped.
- Trashed and historical copies live in the trash/active journals of their own vault and are **not** subject to the live unique-exchange-item-id rule (`XC:608-617` validates live accounts only); undelete runs the collision checks of §11.3 instead.
- The exporter's self-asserted `exporterRelyingPartyIdentifier`/`exporterDisplayName` (`XC:177-178`) may only label the review. There is no "trusted exporter" feature, no trust storage and no auto-apply keyed on it.

### 13.4 Export
User selects a source vault, then items; one vault per handoff; Trash never an export source. The selection sheet shows the **source profile and vault** and is bound to the selected accounts' `(recordID, version, digest)` in that vault, not to the whole head revision: the existing check compares only `snapshot.revision == expectedRevision` (`K:435-438`), so an unrelated write (e.g. passkey `lastSignedAt`, `WSurf/Web/Credentials/WebsiteAuthenticatorCeremony.swift:283-288`) would otherwise invalidate it. If a selected account changed or the vault locked, the sheet is re-opened with the selection preserved and nothing is sent. Private profiles have no vault and are refused (`V:25`). Keep existing exchange ids; never mint ids to influence the importer. Record the §13.2(b) snapshot only after the system reports the handoff `.transferred`, never on `.uncertain` (no automatic retry); `.transferred` is worded "handed to the system", never "Apple imported" (`K:39-47`). Exchange ids are never treated as proof of identity on re-import. Export is `format == .v1` only (`XE:16`) and a 26.4-only FIDO2 metadata item on an older OS cannot be exported (`XE:229`): both fail with a stated message, not a silent omission.

### 13.5 Transfer lifecycle and truthful messaging (fixes R3, R4)
The preview header shows **profile** (name) and **destination vault** (name once unlocked) and is bound to that vault's access epoch and to the `(recordID, version, digest)` of every account the plan touches (`K:209-216` today binds manager+epoch and the whole revision). Apply re-verifies those versions in the commit transaction; an unrelated write to other accounts does not invalidate the preview. A private profile is refused. If two windows of different profiles show the pending token, only the first claimer proceeds and the other visibly loses it. The import binds to the profile whose page the user reviews from (R4); the header makes that visible. Every **failed, cancelled or stale** terminal state has a user-visible message that says the transfer was discarded and must be started again from Passwords (the token is single-use and consumed at claim). A **successful** apply is not a discard: it ends with its result list. "Cleared" never means secure memory erasure: it means WSurf dropped every reference it owns (staged session, preview values, drafts) and refuses further use; Swift, AuthenticationServices and SQLite buffers and copies are not wiped by WSurf and no copy says "erased" or "securely cleared".

| Event | Message semantics |
|---|---|
| second token arrives while one is pending/claimed/staged | "Another transfer is already in progress; this one was not received. Finish or cancel it, then export again from Passwords." (today silently dropped) |
| vault locks, epoch changes, lease expires, user cancels, or an account the plan touches changed since the preview (stale preview) | "This transfer was discarded. WSurf dropped its copy of the imported data and can no longer use it. Export again from Passwords." No data was written (a lock **during** commit is the separate receipt-if-landed case below). |
| apply fails (capacity, collision, write error) | nothing written; state which operation failed; "This transfer was discarded"; start again from Passwords |
| apply succeeds | per-credential result list ("added/replaced in WSurf"); nothing says the Apple side changed; no discard wording |

An import that ends with every item skipped reports "nothing imported", not success (`K:326-328`). A lock during commit is **not** reported as "discarded": it says the write **may** have landed and tells the user to check Saved Credentials (receipt-if-landed, `K:341-347`). Late completions of cancelled operations may neither consume nor clear a successor (existing token/generation binding, `K:142-150`, is kept).

### 13.6 Native acceptance
Behaviour of Apple Passwords (ids, dates, replace semantics, macOS 26.x/27.x) is **UNVERIFIED** until the user runs the §16 acceptance on their own macOS account and Apple Account after delivery (agents never run it). Native checks need a correctly signed build whose app carries `com.apple.developer.authentication-services.autofill-credential-provider`, whose `Info.plist` lists `ASCredentialExchangeActivity` in `NSUserActivityTypes`, and whose extension declares credential-exchange support; whether an ad-hoc or development-signed build receives the activity is not proven. The built extension must have **no** app group or keychain access group (artifact check). The extension stays static: the app is the sole importer/exporter (R7).

## 14. Destination routing (no ambiguity)

A write goes to exactly one named, unlocked vault shown before apply; WSurf never picks "some" vault; locked vaults contribute nothing and are never read.

- **Import:** one destination, shown first; preselect the vault open in Saved Credentials, or the only active vault. Changing it re-runs the preview. Matching/base/`previouslyRemoved` are evaluated in the destination only; other *unlocked* vaults get an informational "same item in vault Y" flag, default skip; the preview states that locked vaults were not checked.
- **Autosave / password update:** to the vault holding the matched account; a match in several unlocked vaults, or none while another vault is locked, requires an explicit choice in the prompt. A new login goes to the **default vault**; if it is locked the prompt asks to unlock or pick, never silent fallback.
- **Passkey registration:** same as autosave; the ceremony keeps its "selected account unchanged after prompts" recheck.
- **Export:** source vault explicit (default: the vault open in Saved Credentials).
- Cross-vault duplicates are allowed, flagged, never merged.

### 14.1 Saved Credentials UI contract (behaviour this design relies on; layout and styling belong to the UI workstream)

- **Vault picker** at the top of Saved Credentials: lists the profile's active vaults (locked ones by ordinal, §4.1) with lock state, marks the default vault, and offers a **default-vault selector** (the §8 step 6 preference). **New Vault** has exactly two choices: *Use existing WSurf passkey* and *New passkey* (§8). Choosing a locked vault offers unlock; nothing of a locked vault's content is shown.
- On the selected vault, two tabs: **Credentials** and **Trash**. Trash lists that vault's linked-trash entries (§11.2) with **Restore** (§11.3; a collision blocks with its reason and offers no alternative), **Purge** and **Empty Trash** (§11.4; fresh native authorization and the §11.4 confirmation). On a credential, **Earlier Versions** lists its password, TOTP and metadata revisions with **Restore** (§11.3a); passkeys have no earlier versions.
- Trash is reachable only as this tab, under its source vault's unlock (§9). It is never a vault in the picker, the default-vault selector, an import destination, an export source, or an autofill/WebAuthn source (§11.2).

## 15. Concurrency, capacity, behaviour at limits

- **Operation lock protocol (one rule, no deadlock).** `Credentials.lock` is an OS `flock` target taken per **operation**, never for the lifetime of a manager, lease, window or the process. Order is always: (1) take the lock, (2) re-read A2/A1/A3 and the v1/stub format under it, (3) open the connection / begin the SQLite transaction, (4) finish, (5) close and release. SQLite's own locks are only ever taken inside steps 3–4. SHARED mode: unlock verification (§6.8), snapshots, commits, vault creation (SQLite `BEGIN IMMEDIATE` then serializes writers across processes). EXCLUSIVE mode: migration, first-vault bootstrap, stub repair, profile erase. A holder **never upgrades**: if under SHARED it learns EXCLUSIVE is needed it releases, reacquires EXCLUSIVE and restarts from step 2, discarding what it read. Acquisition polls `LOCK_NB` for up to 5 s, then fails with `storeBusy` and nothing written. There is no nested lock, so no cycle. Every new-build operation obeys it; old builds never take it and are fenced by the stub (§5) and, at migration, by the atomic swap plus displaced-bytes check (§10), which turn an overlap into preserved evidence instead of a lost write. The in-process mutex stays for access epochs. A stale writer gets `staleRevision`.
- **Capacity:** exact limits are in §5. Live-limit violations are refused whole with a distinct error naming the limit; history has no logical limit; nothing is ever dropped to make room ("drop oldest" does not exist).
- **Disk or SQLite failure:** the transaction rolls back and the **logical committed values** (rows, heads, registry as exposed by the API) are unchanged; physical WAL/page contents may differ and are not claimed identical. **Logical** capacity (the §5 live caps, record admission, active-vault count) never blocks purge or delete; **physical** filesystem exhaustion can fail any transaction including purge, atomically and with an honest message.
- WAL and `-shm` are part of the vault for erase, backup and permissions (`0600`, same directory).

## 16. Acceptance and verification gates (each item is a runnable check or a named user-run native gate)

Unit/integration with synthetic data only (no real vault, no Apple Passwords):

1. Store states: every row of §6.3 (including the new row 13) and every row of §6.9 (DB, registry, one vault, linked trash, stub, A3 and their combinations gone or replaced; `.migrating`/`.swap`/`cutover-v1` leftovers; v1 file reappearing; old-registry replay) yields the stated outcome; Create is offered only in row 10; nothing is moved, deleted or reset by the app in any fail-closed state; the message lists exact paths including `.pre-v2` when present.
2. Authentication: a forged, missing or stale registry, a swapped head/wrapper list, a removed vault or linked trash fails §6.8 step 3 before any grant; RK is verified to be unable to unwrap any DEK (no KDF input, no wrap); stubMissing store gets no mutation or usable access until the stub is re-created under the EXCLUSIVE lock taken **before** the snapshot, and the stub is created with create-if-absent so a v1 file that appeared is never overwritten; **A3 absent with a valid store ⇒ set after authenticated unlock; A3 present and different from a stub/store that agree with each other ⇒ fail closed, no grant, A3 not overwritten, no repair**; creating a vault with another vault locked changes none of that vault's rows/heads/wrappers and decrypts none of them; creating via *Use existing passkey* runs §6.8 steps 1–7 only, never publishes a grant, and leaves the source vault without any lease or autofill availability (§8 item 2); the first vault (including an interrupted bootstrap at each step), *Use existing passkey* (one assertion) and *New passkey* (requires an unlocked vault) paths each work or fail as §8 says.
3. Integrity: tampered/deleted/substituted/replayed/foreign live or history rows (including a row whose stored digest column is wrong but bytes valid, and a row whose ciphertext was swapped with the digest left alone), truncated/reordered/forged journal, missing chain row, transfer-pair mismatch, stale head, wrong profile all fail closed before any grant (V1-V5); no write is possible on a vault whose history failed; verification memory is bounded on a synthetic history of ≥100k rows and ≥1 GB; the scratch file (not `TEMP`, not the OS temp directory) contains only opaque ids/ints/digests (checked by scanning it for a planted secret and name), is `0600` in a `0700` directory, and is removed after success, failure and cancel; leftovers are removed at the next open; the global `temp_store_directory` is never set.
4. Migration: kill at every step boundary of §10 (1–10) leaves v1 or the new store authoritative, never both unrecoverably; wrappers byte-identical and unlock with the original passkey; ids/exchange ids/values unchanged; `.pre-v2` reused only if byte-identical (a different pre-existing file aborts, untouched); a simulated old-build write **before the swap** (v1 changed after B0 was read) is detected at step 8: no grant, displaced file kept as `cutover-v1`, stub and pending store kept, fail closed with paths, nothing merged or rolled back; a simulated old-build write after step 8 yields row 1 or row 3 as stated and nothing is lost; `RENAME_SWAP` unsupported aborts with nothing changed; `.migrating` is never removed before v1 is verified; no open SQLite handle or `-wal`/`-shm` exists on the pending file at rename; checkpoint/close/fsync order observed; resume-at-unlock works and fails closed with paths on a bad `.migrating`.
5. Wrapper AAD frozen: v1 wrappers unwrap in the new store; an old build reading the stub shows the corruption error and never offers Create. Locking: under concurrent unlock verification, commits, vault creation, stub repair and migration attempts (stress, bounded), there is no deadlock; an EXCLUSIVE request waits at most 5 s and then returns `storeBusy` with nothing written; no holder upgrades SHARED→EXCLUSIVE in place; every new-build operation takes the lock before opening SQLite.
6. Revisions: every row of §11.1; a true no-op (identical complete payload) writes nothing; a `lastSignedAt` or import-observation change persists with a head advance and **no** revision, journal row, history row or content `modifiedAt`; 20 TOTP copies + 5 passkey sign-ins create no revision; unchanged draft preserves passkeys/TOTP; removing a password or TOTP by any path moves it and its earlier revisions to Trash and leaves no revision of it in the active vault.
7. Trash: delete→undelete round trip leaves exactly one **logical** owner/location for each record (live in the source vault, none in Trash; "one copy" never means one physical ciphertext) with full history; each collision class blocks; purge needs fresh assertion and its confirmation says it removes the items from WSurf, that encrypted remnants and backups may remain, and names the `.pre-v2` path when present; WSurf never deletes `.pre-v2`; tombstones contain no secret; re-import of trashed/purged item is `previouslyRemoved` and skipped by default.
8. Passkey: same `rpID`+`credentialID` with a different public key **or** different `userHandle` is a hard conflict with no override path at review and codec; an equivalent key with different DER bytes is **not** a conflict; attempting a passkey replace through the review and through the codec is rejected (behavioral tests only; no test asserts the absence of source branches or wiring).
9. Dates: export of an edited account never carries the stale inherited date; migrated/imported `createdAt` nil; WSurf-created sets it.
10. Routing: import into A never touches B; locked vaults unread; default-vault locked ⇒ prompt; autosave ambiguity prompts.
11. Transfer messaging: each §13.5 row shown; token reuse refused; second token not silently dropped; unrelated write between preview and apply does not discard the preview, a change to a touched account does; all-skip is not success; export selection preserved on re-open and `.uncertain` writes no snapshot; whole-payload failure imports nothing and names the record position only.
12. Grants: unlocking vault A with a passkey shared with B does not open B; `removeUnlock` invalidates cached grants and the removed credential cannot open the source or its trash.

13. Capacity and MOVE: deleting then undeleting an account whose history exceeds 32 MB and 1 GB succeeds with bounded memory; **near-cap case:** an account at the live payload cap (≈ 4,000,000 B) with revision rows of comparable size is deleted and undeleted successfully (history rows ≤ the 8,000,000 B cap by construction); injected disk-full/SQLite error mid-MOVE leaves the logical committed values unchanged; purge and delete succeed with live data at the live account/byte caps, at 16 active vaults and with any history size (logical capacity never blocks them); a simulated full filesystem makes purge fail atomically with the honest message; live-limit refusals name the limit.
14. Granularity and restore: deleting one credential leaves the live account, siblings and metadata revisions untouched and moves only that credential's revisions; whole-account delete moves everything; undelete blocks on every §11.3 collision and offers no alternative action; restoring an earlier revision (§11.3a) keeps the chosen revision and makes the current value a new revision.

15. Combined edit: one account holding a password, a TOTP and a passkey is edited in one save that changes the password, the TOTP and the websites together: one transaction, one revision per changed kind, `modifiedAt` set, the passkey byte-identical; a combined save that removes the password, the TOTP and one passkey at once moves each with its own history in one transaction and leaves no active-vault revision of them; restoring an earlier password revision, TOTP revision and metadata revision (§11.3a) each keeps the chosen revision and creates a new revision of the current value; a draft with two website fields containing comma/space/newline-separated entries saves the §12.4 result.
16. Exchange identity: a bound pairing with changed remote password/TOTP is `remote-changed`/`both-changed` (never `ambiguous`); an exchange-id match without a bound pairing is `ambiguous`; only a passkey same-`rpID`+`credentialID` with different key or `userHandle` is a hard conflict; success shows the result list and no "discarded" text; failure/cancel/stale show "discarded" and no "erased" wording; a lock during commit shows the receipt-if-landed message.
17. Secret residue (logical, §11.4): remove a password and a TOTP from an account, edit its metadata, delete and purge it; then open the store with the held DEK, **decrypt and enumerate every currently reachable record** of the vault and its trash (live rows, revision/history rows, Trash entries, tombstones, journal rows, metadata revisions) and assert the planted password and TOTP secrets appear in none of the decrypted plaintexts; the scratch files (plaintext by design) contain no planted secret. A raw plaintext scan of the encrypted store file is **not** evidence (it passes trivially) and is not the test. A metadata revision never contains credential values; an `exchangeMetadata` blob that does not decode as `ExchangeMetadata` refuses the superseding commit. No test asserts zeroization or that freed pages, WAL content or old ciphertext are gone from the file.
18. MOVE journaling: deleting and undeleting an account with **no** history verifies (transfer rows on both journals, empty moved set); a delete → undelete → delete sequence (and a longer alternation) verifies, a historical transfer header is never compared with the current catalogs; a missing, duplicated or mismatched transfer row within a pair, a moved row with a changed origin `version`, or a changed `ownerID`/`subject` fails V5; moved rows with different ciphertext digests but the same key verify.
19. Single-credential undelete: with its owner account live, a password, a TOTP and a passkey entry each restore (the owner's existence, id, exchange ids and origin+username never block); each is blocked by an occupied slot (password/TOTP), by any live passkey with the same `rpID`+`credentialID`, or by another account's overlapping exchange item id / origin+username; a whole-account entry is blocked by each whole-account collision class; the owner missing blocks a single-credential entry.
20. Editor link behaviour: clicking a link in either website field places the caret and never opens a URL or tab (behavioral test on the field's click handling).

### Gate A: PR (automated; no signed artifact, no native claim)

Items 1–20 above as automated tests with synthetic data; the full `xcodebuild test` suite; `Tools/check-format.sh` with the pinned SwiftLint; the coverage floor; a PR into `main` meeting the repository ruleset (`CONTRIBUTING.md`, `RELEASING.md:26-30,175-184`); the exact merged commit's CI green. A PR or feature-branch build is a validation build, not a deployment (`RELEASING.md:28-30`), and says **nothing** about native behaviour. No automated test exercises memory zeroization (not promised), Apple's production UI, or the real vault.

### Gate B: native acceptance (user-run on the user's own account after delivery; **not** a merge or install precondition)

It runs on the **exact artifact G6 installs** (same SHA-256): the clean merged `main` commit, built on Pro after its CI passed, never built or run from the feature branch (`RELEASING.md:28-30`; the established workflow in `docs/superpowers/plans/2026-10-06-linen-upstream-migration.md`, final task). Because it needs the merged commit it is not a PR/merge condition, so nothing is circular. **Direction change 2026-10-12:** the user runs it themselves, on their own macOS account and Apple Account, after G6 has installed the artifact; no disposable macOS user or Apple Account is required. The agents never launch the installed app against production data, never read, export, import or delete the user's real credentials, and no automation drives Apple Passwords or any production UI; the user acts and observes. Because the user's own data is involved, the safety mechanisms stay in force: the migration confirmation (§10), the `Credentials.vault.pre-v2` copy, the pre-install whole-data backup of G6 and the rollback rule. A pass is build-specific evidence, not a guarantee; **none of it may be reported as passed from automation or inferred from a PR build or from reading plists**; everything native stays UNVERIFIED until it passes. First the artifact is checked with `codesign -d --entitlements`: the app has the credential-provider entitlement (`WSurf/WSurf.entitlements:10-11`) and `ASCredentialExchangeActivity` in `NSUserActivityTypes` (`WSurf/Info.plist:76-81`); the extension has its own entitlements (`WSurfCredentialExchange/WSurfCredentialExchange.entitlements:5-12`) and `SupportsCredentialExchange`/version (`WSurfCredentialExchange/Info.plist:27-47`) and **no** app group or keychain access group. If the artifact's signing cannot carry what the native checks need, Gate B is reported **blocked** (not passed, not substituted with another environment, not scope-reduced); whether an ad-hoc or development-signed build works is not proven and not assumed.

- **G1** existing-passkey reuse (§4.3a, §8): with a known-valid PRF credential enrolled in vault S, creating a new vault through *Use existing WSurf passkey* succeeds and the new vault unlocks with that passkey alone, and S was not left open. The error path (distinct message, no fallback) is exercised too, but an "unsupported" error is **not a pass**: if the platform cannot do it, G1 is reported **blocked** and the requested feature is not accepted or reduced.
- **G2** both directions, human-observed on the **receiving** side. Apple→WSurf: the user creates a password, passkey and TOTP item in their own Apple Passwords (preferably new, throwaway items) and exports them; WSurf shows them in review; the operator applies them; the operator observes in WSurf that the password is present and fills the fixture origin, the TOTP shows the same codes as Apple's for the same window, and the passkey signs in at an owned fixture relying party. That fixture (a relying party the operator controls, on an origin they control, covering password, TOTP and passkey checks) is built by plan Task 15; the origin, certificate and DNS/hosts entry are the user's to provide. Without it, the fixture-dependent sign-in checks of G2 are reported **blocked**, not passed; the user may instead check fill and codes against any site they own. WSurf→Apple: the operator exports the same three kinds from WSurf, completes the system handoff, and observes the **receiving records in Apple Passwords**: each present and equivalent (same site, username and password; same TOTP codes; passkey usable at the fixture) or not, recorded either way. WSurf's own UI never claims a per-item receipt or acceptance (§13.1); the operator's observation is test evidence only, never copy.
- **G3** re-import of an edited item: the operator observes whether Apple skipped, added or replaced, and whether ids/dates were stable.
- **G4** migration of the user's real vault, performed only by the user at their own first unlock (§10): they confirm the migration prompt, the original passkey unlocks the migrated vault, and they report the unlock-verification time. Automated agents run no migration on production or copied real data; all §10 steps are exercised on **synthetic** vaults in Gate A (plan Task 9) and the migration's interruption, pre-migration backup and fail-closed behaviour are tests, not Gate B.
- **G5** manual editor smoke in the real app: Return, Shift-Return, Option-Return, keypad Enter, typed comma/Space in both website fields, paste, drop, IME composition, dictation, undo, Tab/Esc, link click (caret only, never navigates), VoiceOver and the accessibility tree of the URL field (role, label, one value per line, link elements) (the §12.4 UNVERIFIED list), and a combined password+TOTP+websites edit with a passkey present (item 15).

It follows the **established** workflow of the plan above, not a new one: CI green on the exact PR-merged `main` SHA; clean merged source built on Pro; the §16 artifact checks pass; quit WSurf so every writer is quiescent (including any old build; fresh Cmd-Q immediately before the swap), then take private (`0700`) consistent backups of the profile data (databases with WAL/SHM consistency, every `Credentials.*` file, settings) and of the previous bundle; replace the bundle **atomically** (copy next to it, then `renamex_np(RENAME_SWAP)`; never delete first); verify the deployed bundle's code signature and the recorded provenance (source SHA, artifact SHA-256 equal to the Pro artifact); verify production data is byte-unchanged (checksums before and after the replace) **before** the user launches it. Production credentials, tabs, profiles and settings are therefore untouched until the user launches; migration of the real vault #1 happens only at the user's first unlock (one-way, §10). The previous bundle and the data backups stay as the rollback and are never auto-deleted; rollback = old app + pre-launch data backup, never the migrated store opened by the old app. Record SHA, artifact hash, backup paths and the authorization. Merging to `main` may start the repository's preview workflow (`RELEASING.md:372-384`) only if its signing credentials and gates are in place; this spec grants no authorization to publish, tag or release anything and asserts no preview is published. ## 17. Not covered / unverified summary
